# A batch manifest must not double-count its sources

A private PDF batch manifest is a mapping: it pairs the before and after source for an opaque public review ID. When a reviewer edits that map to pair a rename, a copy-and-paste error can assign one private source to two IDs. The report then looks as though it reviewed more independent documents than it did.

[PDFFence 1.27.0](https://github.com/SybilGambleyyu/pdffence/releases/tag/v1.27.0) adds a narrow, high-severity batch policy gate for that case: `require_unique_document_sources` (PFP017). It is enabled by the conservative policy generated by `pdffence init`.

## Report a mapping error without reporting the map

PFP017 fails when the exact same private relative manifest path is assigned to more than one public ID on the same before or after side. Every affected ID receives only a generic finding:

~~~json
{
  "rule_id": "PFP017",
  "severity": "high",
  "details": {
    "side": "before",
    "declared_document_count": 2
  }
}
~~~

It does not reveal the root, repeated path, filename, file contents, or hash. SARIF carries no locations or artifact URIs—only the deliberately public review ID and the same generic detail.

## Do not turn identity into a heuristic

The rule only compares equal strict manifest paths on the same side. It does not compare bytes, use filename similarity, infer a rename, or treat hard links and other filesystem aliases as identity. A reviewed one-to-many workflow can disable this one switch explicitly; the tool does not decide that mapping for you.

Exact repeated same-side paths also share one validated snapshot during a batch run, so a duplicate entry cannot multiply parser work thousands of times while the report still remains one result per declared ID.

## Full-corpus evidence

PDFFence 1.27 passed 277 tests, Ruff, bytecode compilation, and dependency consistency checks. The coverage includes before/after-side repeats, opt-in behavior, PFP016 interaction, path-redacted JSON/Markdown/SARIF, location-free SARIF, and single-snapshot reuse.

The 161-entry manifest generated from every [PDFCAB 1.24.1](https://github.com/SybilGambleyyu/pdf-change-benchmark/releases/tag/v1.24.1) pair also ran with PFP017 enabled: 161 changed documents, zero findings. An adversarial manifest reused one real corpus before source under two IDs and produced exactly two PFP017 results, each exposing only `side: before` and `declared_document_count: 2`.

The wheel and source archive build byte-for-byte reproducibly, passed Twine checks, and passed fresh Python 3.12/3.13 installations. The public GitHub assets were re-downloaded, checksum-verified, installed through the published wheel URL, and used for the same checks. A clean dependency audit found no known vulnerabilities.

PFP017 detects an exact mapping mistake. It does not prove a manifest is complete, pair different paths, validate a business decision, render a PDF, compare appearance, validate PDF conformance or signatures, decrypt a source, extract text, execute an action, follow a URI, or detect malware.
